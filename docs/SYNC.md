# ใช้งานหลายเครื่องโดยให้โปรเจกต์อยู่ด้วยกัน

## ปัญหาคืออะไรกันแน่

ตอนนี้โปรเจกต์ถูกเก็บใน **IndexedDB ของเบราว์เซอร์** ซึ่งผูกกับ *เครื่องนั้น + เบราว์เซอร์นั้น +
ที่อยู่ของไฟล์นั้น* เปิดคนละเครื่องคือคนละกล่องข้อมูล ไม่มีอะไรเชื่อมกัน

**เอาโค้ดลง Git ไม่ได้แก้ปัญหานี้** Git ซิงก์ *ไฟล์โปรแกรม* ให้ทุกเครื่องได้ตัวเดียวกัน
แต่ *งานที่วาด* ยังอยู่ในเบราว์เซอร์ของแต่ละเครื่องอยู่ดี — คนละเรื่องกัน

เว้นแต่จะเปลี่ยนให้โปรแกรม**เก็บงานเป็นไฟล์** แทนที่จะเก็บในเบราว์เซอร์ ซึ่งเป็นข้อ 2 ข้างล่าง

---

## สามทางเลือก

### 1. ส่งออก/นำเข้าไฟล์เอง — ทำได้ทันที ไม่ต้องแก้อะไรเลย

เพิ่มปุ่ม **Export Project** (เขียนโปรเจกต์เป็น `.json`) กับ **Import Project**
แล้วเก็บไฟล์นั้นไว้ใน Git, Drive, Dropbox หรือส่งกันทางไหนก็ได้

| | |
|---|---|
| งานที่ต้องทำ | เล็ก — ข้อมูลถูกจัดรูปให้พร้อมเขียนอยู่แล้ว (`packProject`/`unpackProject`) |
| ต้องมีเซิร์ฟเวอร์ | ไม่ |
| ข้อดี | ทำได้เลย · ควบคุมได้เต็มที่ · ใช้กับ Git ได้ตรง ๆ |
| ข้อเสีย | **ต้องกดเอง** ลืมกดคือไม่ตรงกัน · สองเครื่องแก้ไฟล์เดียวกันแล้วชนกันเอง |

เหมาะเมื่อ: ทำงานทีละเครื่อง และอยากได้ประวัติการแก้ใน Git

### 2. เก็บงานเป็นไฟล์ในโฟลเดอร์ที่เลือกเอง — **ทางที่ผมแนะนำ**

ใช้ **File System Access API** ให้ผู้ใช้เลือกโฟลเดอร์หนึ่งครั้ง แล้วโปรแกรม
อ่าน/เขียนโปรเจกต์เป็นไฟล์ในโฟลเดอร์นั้นโดยตรง (เบราว์เซอร์จำสิทธิ์ให้)

ชี้โฟลเดอร์นั้นไปที่ **Dropbox / Google Drive / OneDrive / โฟลเดอร์ Git** — การซิงก์
ระหว่างเครื่องเป็นหน้าที่ของตัวนั้น ไม่ใช่ของโปรแกรม

| | |
|---|---|
| งานที่ต้องทำ | ปานกลาง — เพิ่มชั้นเก็บข้อมูลอีกแบบข้าง IndexedDB (โครงมีอยู่แล้ว: `idbAll` · `idbPut` · `idbDelete`) |
| ต้องมีเซิร์ฟเวอร์ | ไม่ |
| ข้อดี | **ซิงก์เองอัตโนมัติ** · หนึ่งโปรเจกต์ = หนึ่งไฟล์ ทำให้ Git อ่าน diff ได้จริง · ไม่ต้องดูแลอะไรเพิ่ม |
| ข้อเสีย | Chrome/Edge เท่านั้น (Safari/Firefox ยังไม่รองรับ) · เปิดสองเครื่องพร้อมกันแล้วแก้โปรเจกต์เดียวกัน ตัวที่เซฟทีหลังชนะ |

เหมาะเมื่อ: คนเดียวหรือทีมเล็ก หลายเครื่อง ใช้ Chrome — ซึ่งตรงกับที่คุณใช้อยู่

> **ข้อควรระวังเรื่อง Git:** ไฟล์โปรเจกต์เป็น JSON ที่มีพิกัดทุกจุด — ไฟล์ละหลายร้อย KB
> Git เก็บได้แต่ diff จะใหญ่ทุกครั้งที่ขยับอะไร ถ้าจะใช้ Git จริงจังควรเปิด Git LFS
> หรือใช้แค่ Drive/Dropbox ที่ไม่สนใจ diff

### 3. เซิร์ฟเวอร์จริง

โปรแกรมคุยกับ API กลาง โปรเจกต์อยู่ในฐานข้อมูลที่เดียว

| | |
|---|---|
| งานที่ต้องทำ | ใหญ่ — API, ระบบล็อกอิน, การจัดการชนกัน, การดูแลเซิร์ฟเวอร์ |
| ต้องมีเซิร์ฟเวอร์ | ใช่ (หรือใช้ Supabase / Firebase ซึ่งลดงานลงมาก) |
| ข้อดี | หลายคนแก้พร้อมกันได้ · เห็นงานเดียวกันทุกเครื่องทันที · มีประวัติและสิทธิ์เข้าถึง |
| ข้อเสีย | ต้องมีคนดูแล · มีค่าใช้จ่าย · ออฟไลน์ไม่ได้ถ้าไม่ทำเพิ่ม |

เหมาะเมื่อ: **หลายคนแก้แบบเดียวกันพร้อมกัน** — ถ้ายังไม่ถึงจุดนั้น ยังไม่คุ้ม

## ข้อเสนอ

**ทำข้อ 1 ก่อน แล้วค่อยข้อ 2** — ข้อ 1 ใช้เวลาไม่นานและได้ทางออกฉุกเฉินทันที
(ส่งไฟล์ให้กันได้ สำรองงานได้) ส่วนข้อ 2 คือของจริงที่ทำให้ไม่ต้องกดอะไรเลย

**ยังไม่ต้องทำข้อ 3** จนกว่าจะมีคนแก้แบบเดียวกันพร้อมกันจริง ๆ

### สิ่งที่ต้องระวังก่อนซิงก์อะไรก็ตาม

โปรเจกต์ที่บันทึกไว้ **ยังไม่มีเลขเวอร์ชันของรูปแบบข้อมูล** ถ้าเครื่องหนึ่งใช้บิลด์ใหม่
อีกเครื่องใช้บิลด์เก่า แล้วซิงก์กัน จะเกิดปัญหาแบบเดียวกับที่เจอมาแล้วในเซสชันนี้
(ดู `ANALYSIS.md` §8) — ควรใส่ `formatVersion` ลงในไฟล์โปรเจกต์ **ก่อน** เปิดใช้การซิงก์
ไม่ใช่หลัง

## ถ้าจะทำข้อ 2 ให้เริ่มตรงไหน

`src/modules/idb.js` เขียนแยกไว้แล้วเป็นชั้นเก็บข้อมูลที่มีสี่ฟังก์ชัน:
`idbAll` · `idbPut` · `idbDelete` · `storageReport` — และตัวเรียกใช้ไม่รู้ว่าข้างในเป็นอะไร

เพิ่มไฟล์ `src/modules/folder.js` ที่มีสี่ฟังก์ชันชื่อเดียวกัน แต่ทำงานกับโฟลเดอร์
แล้วให้ `load` เลือกว่าจะใช้ตัวไหน — เหมือนตอนที่ย้ายจาก localStorage มา IndexedDB
ซึ่งทำมาแล้วครั้งหนึ่ง (`ANALYSIS.md` §9)

บอก Claude Code แบบนี้ได้เลย:

```
อ่าน docs/SYNC.md แล้วทำข้อ 1 ก่อน: ปุ่ม Export Project / Import Project
เขียนเทสต์ที่ส่งออกแล้วนำเข้ากลับในเบราว์เซอร์คนละตัว แล้ววัดว่าภาพเหมือนเดิมกี่พิกเซล
```
